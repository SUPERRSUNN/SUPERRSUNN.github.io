## nft_table의 취약점
리눅스 커널에는 Netfilter라는 네트워킹 관련 작업을 사용자 정의 핸들러로 구현하기 위한 프레임 워크가 존재한다. nftables는 모듈로서 커널에 부착할 수 있는 기능으로 패킷을 필터링 하거나 라우팅하는 기능을 제공한다. nftables는 tables, chains, rules, exressions로 구성된다. 각 구성 요소는 순서대로 포함관계를 가진다. 패킷은 각 단계를 거쳐 rules에서 규칙에 맞게 평가한다. 또한 이 규칙을 정의 할 때 sets를 활용한다. sets는 여러 IP, 포트 등이 사용될 때 이를 element란 자료로 나타내 묶어 규칙에 추가하는  묶음이다. CVE-2022-43918은 이 sets에 element를 추가하는 과정에서 발생하는 취약점이다. 주목해야 할 함수는 nft_add_set_elem, nft_setelem_parse_data, nft_set_elem_init 함수이다. 다음 소스 코드를 보라.

nft_add_set_elem은 사용자가 sets에 element를 추가하려고 할 때 호출되는 함수로 nft_setelem_parse_data 함수 호출을 통해 추가하고자 하는 element의 유효성 검사 및 element를 파싱해서 적절한 구조체로 할당하는 역할을 담당한다.
nft_set_elem_init 함수에서는 커널의 동적 할당 메커니즘을 활용해 적절한 공간을 만들고 해당 공간에 element의 정보들을 넣어둔다. 취약점은 nft_setelem_parse_data에서 발생한다. 다음 소스 코드를 보라.  
{% highlight c %}

static int nft_setelem_parse_data(struct nft_ctx *ctx, struct nft_set *set,
                  struct nft_data_desc *desc,

{
    int err;

    err = nft_data_init(ctx, data, NFT_DATA_VALUE_MAXLEN, desc, attr);          <=====
    if (err < 0)
        return err;

    if (desc->type != NFT_DATA_VERDICT && desc->len != set->dlen) {             <=====

주목해야 할 부분은 if (desc->type != NFT_DATA_VERDICT && desc->len != set->dlen)이다. 여기서 타입이 NFT_DATA_VERDICT일 경우 && 연산자 규칙에 따라 뒤의 desc->len가 set->dlen와 같은 지 확인하는 연산을 생략한다. 여기서 desc->len은 사용자가 실제로  
넣고자 한 element의 길이이고, set->dlen은 sets를 생성하는 과정에서 설정한 데이터의 길이이다.   다음의 nft_set_elem_init 함수의 소스 코드를 보자.

element를 할당하기 위한 공간은 kzalloc(set->ops->elemsize + tmpl->len, gfp)로 만들어지는데 여기서 tmpl->len은 desc->len을 참조하여 만들어진 값이고, 이 캐시로의 데이터 복사는 memcpy(nft_set_ext_data(ext), data, set->dlen)가 담당하여, set->dlen만큼이 이루어진다. 즉 element의 타입이 NFT_DATA_VERDICT일 경우 힙에 쓰는 값이 해당 공간의 크기보다 큰, 즉 버퍼 오버플로우가 발생할 수 있다. set->dlen은 sets를 만드는 과정에서 64바이트까지 설정할 수 있으며, NFT_DATA_VERDICT 타입인 경우 set->ops->elemsize + tmpl->len는 사용자가 key를 적당히 설정하여  64바이트가 할당되게 할 수 있다. 다음 그림을 보자.  
![](/assets/images/element.png)
그림과 같이 16바이트의 NFT_DATA_VERDICT 뒤의 kmalloc-64에 들어있는 구조체를 corrupt시킬 수 있다. 여기서 set->dlen을 64바이트로 설정했을 경우 NFT_DATA_VERDICT의 시작점부터 채우기 시작해 48바이트를 corrupt 시킬 수 있다.
여기서 memcpy(nft_set_ext_data(ext), data, set->dlen)가 가져오는 값 data는 nft_set_elem_init의 매개변수이므로 스택의 값을 가져온다. 단순히 set->dlen을 64바이트로 설정하고 NFT_DATA_VERDICT element를 쓰려고 하면 스택 내의 임의의 48바이트를 corrupt 시킨다.

nla_for_each_nested는 일종의 반복문을 구현한 매크로로 이를 순회하면서 nft_add_set_elem을 호출함을 볼 수 있다. 이 매크로는 nft_add_set_elem을 연속 호출한다. 따라서 첫 번째 nft_add_set_elem을 호출했을 때 스택을 원하는 값으로 채워넣으면 두 번째 nft_add_set_elem 호출에서는 값을 적은 위치로 돌아와 해당 값 위에 인자를 넣으므로 이를 통해 48바이트를 조작 할 수 있다.

익스플로잇 흐름은 덮어쓰고자 하는 64바이트 크기의 구조체 스프레이 -> sets->dlen이 64인 sets 생성 -> NFT_DATA_VALUE 타입의 element를 16바이트의 더미, 48바이트의 원하는 값으로 적기 -> NFT_DATA_VERDICT 타입의 element 할당 시도 -> overflow  
와 같이 이루어 진다. 이제 LPE를 구현하기 위한 KASLR Leak, Arb_write를 트리거 하는 데 사용될 kmalloc-64의 구조체들을 알아 보자.  
  
## KASLR Leak

KASLR Leak에 사용될 구조체는 add_key 시스템콜로 할당 가능한 struct user_key_payload와 io_uring_setup 시스템콜로 할당 가능한 struct percpu_ref_data를 사용할 수 있다. 

{% highlight c %}

struct user_key_payload {
        struct rcu_head rcu;            /* RCU destructor */
        unsigned short  datalen;        /* length of this data */
        char            data[] __aligned(__alignof__(u64)); /* actual data */
};


struct percpu_ref_data {
        atomic_long_t           count;
        percpu_ref_func_t       *release;
        percpu_ref_func_t       *confirm_switch;
        bool                    force_atomic:1;
        bool                    allow_reinit:1;
        struct rcu_head         rcu;
        struct percpu_ref       *ref;
};
 
{% endhighlight%}

user_key_payload는 일종의 헤더 역할을 하는 구조체로 datalen에 들어있는 값과 size(user_key_payloads)를 더한 값 만큼의 할당이 이루어지며, datalen는 사용자가 임의로 지정할 수 있다. 이를 통해 크기를 64바이트에 맞추고 overflow를 활용해 datalen을 큰 값으로 덮어씌워주면 임의의 주소의 값을 읽어 올 수 있다. percpu_ref_data는 64바이트 크기의 구조체로 해당 구조체 내부의 release에는 io_ring_ctx_ref_free 함수의 주소가 ref에는 kzalloc으로 할당받은  힙의 주소가 저장되며 이를 각각 활용하여 
KASLR base와 physmap base 주소를 구할 수 있다. 

## Arb Write
  
임의 쓰기는 simple_xattr 구조체를 이용해 진행된다. simple_xattr은 특정 파일 시스템에서 파일에 확장 속성을 부여하는 구조체이며 다음과 같다.  
{% highlight c %}

struct simple_xattr {
        struct list_head           list;                 /*     0    16 */
        char *                     name;                 /*    16     8 */
        size_t                     size;                 /*    24     8 */
        char                       value[];              /*    32     0 */

        /* size: 32, cachelines: 1, members: 4 */
        /* last cacheline: 32 bytes */
};

struct list_head {
        struct list_head *next, *prev;
};

static inline void __list_del(struct list_head * prev, struct list_head * next)
{
        next->prev = prev;
        WRITE_ONCE(prev->next, next);
}

{% endhighlight%}

simple_xattr은 이중 연결 리스트로 관리되는 데 이 중 하나를 제거하는 함수 \__list_del을 이용해 입의 쓰기를 수행한다. next에 원하는 값, prev에 원하는 주소를 덮어쓸 경우 WRITE_ONCE 매크로에 따라 해당 주소에 원하는 값을 쓸 수 있다. simple_xattr의 valu
는 사용자가 임의로 지정한 크기의 리스트가 되므로 이를 64바이트에 맞게 설정하고 스프레이한뒤 overflow를 진행하면 임의 쓰기를 획득할 수 있다. 이번 익스플로잇에서는 modprobe_path란 변수의 값을 바꾸는 방식으로 LPE를 트리거한다. modprobe_path에 저장된
값은 일반적으로 /sbin/modprobe로 이 경로는 리눅스에서 알 수 없는 형식의 파일이 실행되려고 할 경우 해당 경로의 파일이 root 권한으로 실행된다. 따라서 shell을 실행하는 임의의 바이너리를 만들고 해당 경로를 modprobe_path 변수에 넣으면 루트 쉘을 안정적
으로 획득 할 수 있다. 

## 실습
  
해당 취약점은 5.18.9 버전까지 존재한 취약점으로 해당되는 버전은 아무거나 상관 없으나 5.15.1 버전으로 진행해 보았다. 커널을 빌드할 때 필수적으로 nftables 옵션을 활성화해서 빌드해 주여야 한다. 해당 옵션은 모듈 또는 내장으로 선택하여 포함시킬 수 
있으나, qemu 환경에서 모듈을 추가하는 것이 쉽지 않으므로 내장하는 것을 추천한다. 또한 디버깅을 용이하게 하기 위한 옵션들을 임의로 추가할 것을 권장한다.  

gdb의 경우 커널 디버깅 전용 gef를 사용했다.  [Link](https://github.com/destr4ct/gef-kernel)
